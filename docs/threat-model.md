# Threat model

Baukit foundation, written with `agent-skills/skills/baukit-threat-model`. Last reviewed: 2026-11-25, on top of commit f22e039f (P-07 to P-17), with the drift fixes, high findings and new boundaries from the correctness verification work. `docs/verification.md` lists what each proof covers.

Baukit is a library, so this model covers the controls the crates, packages, templates and edge config provide, and the threats they cover for a product that uses them as generated. Each product keeps its own `docs/threat-model.md` for routes, data and integrations it adds. Gaps S-01 to S-11 come from the security catalog in the [quality and security plan at v0.31.0](https://github.com/PatrickKoss/baukit/blob/v0.31.0/docs/quality-security-plan.md).

## Data classes

| Class | Kind | Stores | Retention and erasure |
|---|---|---|---|
| Identity claims (subject, email, org) | personal | PostgreSQL via `baukit-auth` principal, logs as hashed or bounded fields | `baukit-erasure`, `baukit-data-subject` |
| Access and refresh tokens | credential | browser storage via `@baukit/auth-web` (S-01), native secure store via `@baukit/auth-native` | token lifetime |
| API tokens | credential | PostgreSQL, hashed (`baukit-auth/src/api_token.rs`) | revocation and expiry |
| Pending OAuth flows (state hash, binding hash, user, provider, PKCE verifier) | credential | PostgreSQL `oauth_states` and `oauth_states_used` via `baukit-integrations` `oauth-state` | 10 minute TTL, `purge_expired` |
| Third-party secrets | credential | PostgreSQL, AES-256-GCM (`baukit-credential-vault`) | deleted with the connection |
| Synced user content | product-defined | PostgreSQL, device SQLite and IndexedDB (`@baukit/data-contracts-*`) | `baukit-sync` purge horizons |
| Media | content | object storage behind the njs edge | product-defined |
| Telemetry and analytics | operational | `baukit-telemetry`, `@baukit/analytics-*` | collector retention |

## Trust boundaries

| Boundary | Entry points | Identity |
|---|---|---|
| browser and native app to API | `baukit-http` router, sync push and pull | OIDC, Clerk or WorkOS bearer, API token |
| MCP client to MCP endpoint | `baukit-mcp` HTTP transport | bearer or API token, Origin allowlist |
| client to njs media edge | grant query string | HMAC grant |
| IdP to API | discovery and JWKS fetch | issuer URL |
| API to third parties | `baukit-egress` `GuardedClient` | product credentials |
| OAuth provider redirect to API callback | `baukit-integrations` `oauth_state` complete, `__Host-baukit-oauth` cookie | single-use `state` bound to the starting browser |
| inbound webhooks and suite hub | `baukit-core` webhook signatures, `baukit-suite` receiver | shared secret or peer signature |
| tenant GitOps repository to cluster | Flux Kustomizations and HelmReleases in a namespace labelled `baukit.dev/tenant=true` (`deploy/platform/components/tenant`) | the tenant's `flux-reconciler` ServiceAccount, impersonated by kustomize-controller and helm-controller |
| tenant custom resources to platform controllers | Flagger `Canary` and `MetricTemplate`, Traefik `IngressRoute`, `Middleware` and `TraefikService`, Prometheus Operator `ServiceMonitor` in a tenant namespace, granted to `admin` by `baukit-tenant-*` ClusterRoles in the flagger, traefik and observability-stack bases | Flagger, Traefik and Prometheus, each acting with its own pod identity and network reach |
| Flagger to tenant metrics proxy | `tenant-metrics-proxy` Service in each tenant namespace (prom-label-proxy, plain HTTP on 8080), forwarding to the platform Prometheus | none on the listener; NetworkPolicy admits only Flagger pods in `flagger-system`, and the proxy's label value is fixed by flag |
| API server to Falco audit webhook | k8saudit plugin on `falco-k8saudit-webhook` (`10.43.0.60:9765/k8s-audit`, plain HTTP inside the cluster) | none on the listener; NetworkPolicy admits the node CIDR only |
| client device as a multi-user store | `data-contracts` `ScopedPersistenceLifecycle`, store registry and web storage; `api-runtime` 401 signals; sync adoption; the device erasure flow | one session token shared by every tab; one partition per subject |
| release pipeline | `.github/workflows/release.yml` on any `v*.*.*` tag; crates.io and npm publish with `id-token: write` | whoever can push a tag |
| push token registration | `baukit-push` device registry (`rust/crates/baukit-push/src/postgres.rs`) | registering user's bearer; the Expo token is the primary key |
| data-subject machine API | `baukit-data-subject` server router (`rust/crates/baukit-data-subject/src/server/router.rs`) | allowlisted OAuth `client_id` with the data-subject scope |
| API to OTLP collector | `baukit-telemetry` OTLP exporter (`rust/crates/baukit-telemetry/src/lib.rs`) | collector endpoint from config |
