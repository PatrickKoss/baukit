{% endif %}## Native QA

Android builds require Java 25. `corepack pnpm android` and the QA targets grant native access to Android's Prefab tool. Use `bash scripts/android-java.sh ./android/gradlew` with your Gradle arguments for direct builds.

The local QA targets start disposable PostgreSQL, Redis{% if context.auth_enabled %}, Keycloak{% endif %} and API instances on separate ports.{% if context.auth_enabled and not context.auth_oidc %} The API verifies the local realm's tokens, and a placeholder stands in for the provider deletion key unless `{{ context.app_env }}__AUTH__IDENTITY_ADMIN_CLIENT_SECRET` is set.{% endif %} They install an embedded release build in a dedicated emulator or simulator, so Metro is not required.

```sh
make qa-android          # interactive Android emulator
make e2e-android-live   # Maestro against the open emulator
make qa-android-down

make qa-ios              # interactive iOS Simulator, macOS only
make e2e-ios-live       # Maestro against the open simulator
make qa-ios-down
```

Use `make e2e-android` or `make e2e-ios` for one disposable automated run. Mobile-only products expose the same targets through `make -C mobile`. Android supports Linux and macOS. iOS requires macOS, Xcode with a Simulator runtime, and CocoaPods. Maestro is required only for the `e2e-*` targets.

The generated `.maestro/smoke.yaml` signs in with the local test account{% if not context.auth_oidc %} through Keycloak{% endif %}, reaches the main screen, and persists analytics consent. Add product critical paths beside it. QA state and logs live under `.qa/`; generated native projects and build output are ignored by Git. `qa-down` removes only the QA compose project's volumes.

The Baukit packages come from {{ context.baukit_typescript_dependency_description }} and the generated lockfile makes the first install reproducible. Native compilation is outside the portable CI gates; run `corepack pnpm@12.9.1 typecheck`, `corepack pnpm@12.9.1 lint`, and `corepack pnpm@12.9.1 test`.

## Purchases

`src/purchases.ts` builds one `PurchaseFlow` from `@baukit/purchases-core`. With `EXPO_PUBLIC_REVENUECAT_IOS_API_KEY` or `EXPO_PUBLIC_REVENUECAT_ANDROID_API_KEY` set it uses RevenueCat. Without them it uses the no-op port and the app behaves as before. `AppShell` provides the flow and resets it on sign-out. Call `purchaseFlow().identify(suiteSubject)` after sign-in and replace the standalone entitlement backend when the product joins the suite. Baukit's `docs/platform/mobile-purchases.md` has the full order.

## Delete profile

The Identity section links to `/delete-profile`. The screen requires a second explicit
confirmation to delete the profile data and sign-in account. Its service uses
`DELETE /me` and keeps the idempotency key in Expo SecureStore under a hashed account
slot. A dropped response keeps local data and authentication for a safe retry.
A completed or pending receipt removes the key from device storage.

After a completed or pending receipt, the service erases the local account
partition and clears authentication. A pending result explains that sign-in
account deletion is still finishing. The screen automatically polls the operation
with bounded backoff and the token captured before sign-out. Leaving the screen
aborts polling. If the operation is still pending at the bound, the status button
starts another round. An expired token ends polling and explains that deletion
continues on the server without user action. A failed operation asks the user to contact
support; it does not offer another deletion. Preparation failures explain that
the request was not sent and offer a retry. English and German strings live
in `src/delete-profile-copy.ts`.

Navigation changes can mount `src/delete-profile-screen.tsx` through the
existing route. Keep the route mounted after local sign-out so the pending
result stays visible. The server must implement the profile-erasure HTTP
contract and its identity deletion worker.
