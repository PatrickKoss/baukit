# Other deferred contracts study

## Question and scope

This study checks whether the stated next evidence for each deferred candidate now exists in Tiefgang, Leitbild, Redemut, or Eigenruhe. A present result means the candidate may receive a separate focused study or may already be covered by Baukit. It does not authorize package work here. Fitness Tracker is not checked out on this machine, so the celebration comparison cannot be performed; the decision follows [ADR 0001](../adr/0001-product-experience-package-boundaries.md) and the current platform contracts where that repository was required.

## Candidate interface or contract sketch

No single interface spans this deferred list. The present evidence supports only these bounded follow-ups:

- SQLite migration conformance should accept a product driver fixture and assert monotonic versions, one-migration rollback, restart after failure, and rejection of a database version newer than the application.
- Sync should remain callback composition. New shared work should be an assertion added to existing sync conformance only when the same invariant appears in Eigenruhe, Tiefgang, and Redemut.
- MCP helpers may accept a product error mapper and logger, return MCP `content` and `isError`, preserve bounded request metadata, and never expose raw exceptions or backend bodies. Structured output support needs an explicit compatibility policy.
- Minimal Rust images need no new interface. The generated Dockerfile target names and non-root distroless runtime are the existing contract.

## Decision

Decision: defer until each row's stated evidence is present and its focused study is complete. SQLite migrations and MCP helpers may now move to separate contract studies. Sync comparison is complete enough to keep the coordinators local and put only repeated invariants into conformance. Minimal runtime images are already covered by the generated Dockerfile pattern. No package, template, or broad deferred-contract API should be created from this catch-all item.

## What stays product-owned

Products keep content schemas and build metadata, private artifact records, celebration events and presentation, component markup and styling, secret-link purpose and leakage policy, SQL and schema versions, gate names and provider availability, extension permissions and lifecycle, sync protocols and recovery, media providers and uploads, prompts and model mappings, process contents, MCP tools and domain errors, cache keys and invalidation, Markdown dialect and sanitizer, word-count meaning, and dialog UI and copy.
