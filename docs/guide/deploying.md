# Deploy a product to testing and production

At the end of this page your product builds signed images on every push to `main`, Flux rolls them out to a testing namespace, and a manual workflow promotes the same digests to production. The page is for product developers who generated a backend with `baukit new` and now need it running on a cluster.

## What the pieces are

A deploy combines four things from baukit:

- `backend/Dockerfile`, rendered from `[backend.image]` in `baukit.toml`.
- The `baukit-app` Helm chart in `deploy/chart/baukit-app/`. It runs the API, an optional worker, the migration Job, an opt-in seed Job and optional Redis.
- `deploy/gitops/` in the product, with a shared `base/` and one overlay each for `testing/` and `production/`. Flux applies them.
- `.github/workflows/release.yml` and `promote.yml` in the product, with `scripts/release.sh` and `scripts/promote.sh` behind them.

The cluster side, meaning Flux, the tenant namespace, the shared PostgreSQL and the age identity, lives in a separate platform repository. [Run the local platform](local-platform.md) covers a cluster you can try this on.

## Build the image

The CLI renders `backend/Dockerfile`. Do not edit it by hand. Its first lines say so:

```dockerfile
# Generated by Baukit. Edit backend.image in baukit.toml, then run baukit generate dockerfile.
```

Change the image in `baukit.toml` under `[backend.image]`, then render again:

```sh
baukit generate dockerfile
baukit generate dockerfile --check   # fails if the committed file differs from the render
```

`[backend.image]` accepts `binaries`, `bin_crate`, `backend_context`, `cargo_build_jobs`, `build_inputs`, `pre_build`, `runtime_files`, `runtime_binaries`, `runtime_packages`, `variants`, `writable_directories`, `downloads` and `apt_packages`. The struct is `BackendImage` in `cli/src/dockerfile.rs`, and unknown keys fail. The [manifest guide](manifest.md) explains each key. The section needs `backend = true`, `binaries` must not be empty, and `cargo_build_jobs` must be positive.

Each process gets its own image: `api`, `migrate`, and `worker` when the product has one.

## Add the GitOps files

A product generated with `--backend` already has `deploy/gitops/` and both workflows. An older product adds whatever is missing:

```sh
baukit generate gitops
```

The command writes only files that do not exist yet. It fails when `baukit.toml` has `backend = false`.

The overlays read their identity from `[gitops]` in `baukit.toml`:

```toml
[gitops]
domain = "lab.example.com"
registry = "ghcr.io/example"
```

`lab_registry`, `identity_url` and `realm` are optional. Change them there and regenerate, or edit the files under `deploy/gitops/` directly, because they belong to the product.

The rendered `deploy/gitops/README.md` in the product is the full reference for this layout. It comes from `templates/backend/deploy/gitops/README.md`.

## Testing and production namespaces

Both environments run in their own namespace on the same platform:

| Environment | Namespace | Host |
|---|---|---|
| testing | `<app>-testing` | `<app>-testing.<domain>` |
| production | `<app>-production` | `<app>.<domain>` |

Each runs one replica and has its own database, reached through the `<app>-runtime` Secret. Postgres defaults to a database on the shared platform cluster. Redis defaults to off. Each overlay can switch either one to a shared or dedicated mode by adding one entry from `backing/` to its `components` list. The product's `deploy/gitops/README.md` lists the modes and the Secrets each needs.

## Where the chart comes from

The generated `base/chart-source.yaml` is a Flux `GitRepository` named `baukit`. It points at `https://github.com/PatrickKoss/baukit.git` at the tag `v<template version>` and keeps only `deploy/chart/baukit-app/`. The HelmRelease in `base/helmrelease.yaml` loads the chart from that source with `chart: ./deploy/chart/baukit-app`.

The chart README shows a Helm dependency on `oci://ghcr.io/patrickkoss/charts`. No workflow in `.github/workflows/` packages or pushes the chart, so that repository is not filled by baukit's release. Use the Git source the templates generate, or vendor the chart directory at a tag.

Every image needs `image.tag` or `image.digest`. The chart has no default tag and rejects `latest`. The [chart README](../../deploy/chart/baukit-app/README.md) lists every value.

## Migrations run as a release Job

The chart renders `migration-job.yaml` as a Helm `pre-install,pre-upgrade` hook. `migration.enabled` defaults to `true`, and the Job runs `/app/migrate` from the migrate image. The API never migrates on startup.

The Job connects as the database owner. That is the tenant role on shared Postgres, or `app` on a dedicated cluster. Neither is a superuser. A migration that creates roles needs `owner_create_role = true` under `[postgres]` in `baukit.toml`, and that needs dedicated Postgres in every environment. `baukit doctor` fails otherwise. The product's `deploy/gitops/README.md` lists the role rules that follow from PostgreSQL 16.

Locking and expand, migrate, contract ordering stay the application's job. See [ADR 0026](../adr/0026-reference-sql-migrations.md).

## Secrets with SOPS

The `*.enc.yaml` files under `deploy/gitops/` start as plaintext placeholders. Put the tenant's age recipients into `deploy/gitops/.sops.yaml`, fill in the values, and encrypt each file in place:

```sh
sops --config deploy/gitops/.sops.yaml --encrypt --in-place deploy/gitops/testing/runtime-secret.enc.yaml
```

Source: `templates/backend/deploy/gitops/README.md`. `scripts/release.sh` and `scripts/promote.sh` refuse to run while any `*.enc.yaml` lacks SOPS metadata, so a plaintext secret cannot reach the GitOps branch through them.

## Release and promote

`release.yml` runs `scripts/release.sh` on every push to `main` that changes something outside `deploy/gitops/`. The script:

1. builds each process image,
2. pushes `<registry>/<app>-<process>:<sha12>`,
3. signs each image by digest with cosign,
4. commits the `<sha12>@sha256:<digest>` pins to `deploy/gitops/testing/release.yaml`.

Flux picks up the commit and upgrades the testing HelmRelease.

With `lab_registry` set, the release also copies each image and its signature to the lab registry with `cosign copy`. The digest stays the same, so the pins and signatures hold in both registries.

`promote.yml` is manual. It verifies the signatures with `deploy/cosign.pub` and copies the pins to `deploy/gitops/production/release.yaml`. Try either script locally first:

```sh
scripts/release.sh --dry-run
scripts/promote.sh --dry-run
```

The dry run prints the commands without building, pushing or signing.

## Repository setup

The workflows need this in GitHub:

- an environment `release`, limited to `main`, with the secrets `COSIGN_PRIVATE_KEY`, `COSIGN_PASSWORD` and `GITOPS_DEPLOY_KEY`
- an environment `production` with a required reviewer and the secret `GITOPS_DEPLOY_KEY`
- a deploy key with write access, whose private half is `GITOPS_DEPLOY_KEY`, allowed to bypass branch protection on `main`
- `deploy/cosign.pub`, the public half of the cosign key, committed by you
- with `lab_registry`, the variable `LAB_REGISTRY_USER` and the secret `LAB_REGISTRY_TOKEN` in `release`

`BAUKIT_RUNS_ON` and `BAUKIT_GATE_RUNS_ON` are optional repository variables. Each holds a JSON runner label array such as `["self-hosted","lab","x64"]`. Unset, the jobs run on `ubuntu-latest`.

## Smoke a deploy on a throwaway cluster

`deploy/smoke/k3d-smoke.sh` deploys already-built images to a new k3d cluster, installs `baukit-app` and the observability provisioning chart, calls the API with a token, checks metrics and log redaction, and deletes the cluster on exit. It builds nothing and holds no product logic.

It needs four settings:

| Setting | Purpose |
|---|---|
| `BAUKIT_SMOKE_PRODUCT` | product name and default namespace and release prefix |
| `BAUKIT_SMOKE_VALUES_FILE` | product values file for `baukit-app` |
| `BAUKIT_SMOKE_IMAGES` | local images to import into k3d, dependencies included |
| `BAUKIT_SMOKE_TOKEN_COMMAND` | executable that writes one access token to `BAUKIT_SMOKE_ACCESS_TOKEN_FILE` |

The harness creates the product namespace with Pod Security `restricted` and fails if a pod violates it. The [smoke README](../../deploy/smoke/README.md) lists the optional settings.
